# Phase 1.2 数据库统一数据模型 — 业务对象确认书（产品经理输入）

> 阶段：Phase 1.2 数据库统一数据模型设计
> 角色：产品经理（许清楚）
> 日期：2026-11-12
> 用途：本文件为系统架构师（高见远）进行 Phase 1.2 数据库建模提供**业务层面**的核心需求依据。凡标注"业务已确认（确定）"的内容为产品要求的既定事实，建模时必须满足；凡标注"需架构师决策"的内容为须由架构师在建模层面拍板的技术决策项。
> 原则：本文件只定义业务对象与业务规则，**不写正式数据模型**（表格字段/主外键/FTS 索引归属架构师职责）。本文件覆盖 6 大核心数据域，禁止任何硬编码具体船型/项目/单位/专业。

---

## 0. 全局设计约束（所有域通用）

| # | 约束 | 说明 |
|---|---|---|
| G1 | 多项目/多组织/多专业/多区域/多系统 | 所有业务对象必须通过关联表挂在项目/组织平面上，任何表不得内嵌单一船/项目/单位/专业的字面值。 |
| G2 | 来源可追溯 | 一切"业务事实"（问题/风险/决策/任务/知识）必须有来源(sources)，源可指向邮件/文档/图纸/会议/消息/计划等。 |
| G3 | 物理隔离 | 与旧知识库 `D:\ALLAN\个人知识库` 严格隔离，全新建模，不复制旧结构。 |
| G4 | 版本化 | 文档、图纸、计划、知识均需版本管理；基线(baseline)受保护。 |
| G5 | 信息性质分层 | 所有可被 AI 加工/评定的内容须带"信息性质"标签，取枚举：`SOURCE_FACT / CONFIRMED_FACT / AI_INFERENCE / PREDICTION / PROPOSAL / DECISION`。 |
| G6 | 文本可检索 | 所有承载内容的文本表须挂 FTS5 trigram 索引（中文检索）。属架构师工具面，业务上要求"任意自然语言可搜到相关实体"即可。 |
| G7 | 禁止硬编码 | 禁止出现 `ship = 'XXX'`、`discipline = XXX` 之类写死。 |

## A. 核心业务对象清单与对象间业务关系

### A.1 项目与组织域

| 对象 | 一句话定义 |
|---|---|
| Project（项目） | 一次造船/改造工程，是全部业务数据的总根。 |
| ProjectPhase（项目阶段） | 项目内的 EPCS 阶段实例（同一项目可有多个阶段实例，如多轮工程迭代）。 |
| Organization（组织） | 参与方：船东、船厂、设计院、分包商、供应商、监理等。 |
| Person（人员） | 个人参与者（组织下的人）。 |
| ProjectMember（项目成员） | 人员在特定项目内承担的角色/职责（同一人可参与多项目）。 |
| Department（部门） | 组织内部部门。 |
| Discipline（专业） | 专业维度：船体、轮机、电气、舾装、涂装、内装、暖通等。 |
| Area（区域） | 区域维度：分段、总段、舱室、甲板、机舱、上层建筑等（空间/安装位置）。 |
| System（系统） | 系统维度：压载系统、消防系统、电力系统、主机推进等（功能系统）。 |
| Equipment（设备） | 设备维度：主机、发电机、泵、阀、控制台等（可追溯到采购与图纸）。 |

**对象间业务关系（业务确认）**
- Project → ProjectPhase = **1 对多**（一个项目可有多个 EPCS 阶段实例）。
- Project → Organization = **多对多**（经 ProjectMember 承担角色实现），即"项目×组织×角色"三维。
- Organization → Person = **1 对多**。
- Project ↔ Disciplin/Area/System/Equipment = 各有独立的 **多对多** 关联（项目可以横向施加专业/区域/系统/设备，且可能跨项目共享标准件目录——见 OQ）。
- Equipment 挂在一棵分类树 / 挂 System，System 挂专业：`Equipment→System→Discipline` 层级引导，但允许 Equipment 直接挂 Project（采购先于系统定型）。
- 该域核心是"把任何对象锚定到 Project 平面 + 多组织平面"，是其余 5 域的挂载底座。

### A.2 计划管理域

| 对象 | 一句话定义 |
|---|---|
| Plan（计划） | 一份计划（L1 总计划 ~ L4 周计划），按粒度/周期区分。 |
| PlanVersion（计划版本） | 同一计划的不同迭代版本。 |
| BaselineVersion（基线版本） | 已批准、受保护的里程碑基线。 |
| PlanActivity（计划活动） | 计划中的单个活动/作业。 |
| Milestone（里程碑） | 关键节点（可视为一种特殊活动）。 |
| ActivityDependency（活动依赖） | 活动间的前后置关系（FS/SS/FF/SF 及 lag）。 |
| ProgressRecord（进度记录） | 活动在时点上的实际进度/完成情况/百分比。 |

**对象间业务关系（业务确认）**
- Project → Plan = **1 对多**。
- Plan → PlanVersion = **1 对多**；Plan → BaselineVersion = **1 对多**（同一计划可有多个已批准基线，但同一时刻仅一个"当前生效基线"）。
- Plan → PlanActivity = **1 对多**；PlanActivity → ActivityDependency = **1 对多**。
- PlanActivity ↔ PlanActivity = **自关联/多对多**（经 ActivityDependency 表实现前后置）。
- PlanActivity → ProgressRecord = **1 对多**（进度历史）。
- Milestone 可视为 PlanActivity 的**子类型**（或带 is_milestone 标记），不用重复建模。
- 计划内活动可与**问题/风险/任务/决策**多对多关联（见 A.4 闭环）。
- 滚动预测：以 PlanVersion 的多次发布表达"滚动更新"，非数据模型中单独造表。

### A.3 信息与文件域（来源域）

| 对象 | 一句话定义 |
|---|---|
| Email（邮件） | 一封原始邮件（含元数据；正文按隔离边界授权处理）。 |
| EmailAttachment（邮件附件） | 邮件的附件（可为文件或后续升级为 Document）。 |
| Document（文档） | 人工上传/接收的文档（Word/Excel/PPT/PDF 等）。 |
| DocumentVersion（文档版本） | 文档的版本历史。 |
| Drawing（图纸） | DWG/图纸类，A.1 中 Area/System/Equipment/Ship 的承载。 |
| DrawingVersion（图纸版本） | 图纸版本历史（含 revision）。 |
| Meeting（会议） | 一次会议（含录音转写）。 |
| MeetingMinutes（会议纪要） | 会议的纪要/决议产出。 |
| Message（消息） | 微信/即时消息。 |
| Evidence（证据/凭证） | 用于佐证某一业务事实的一条具体情境/附件/截图等。 |
| SourceReference（来源引用） | 泛化的"来源"桥——统一把任一业务对象指向任何来源载体。 |

**对象间业务关系（业务确认）**
- Email → EmailAttachment = **1 对多**。
- Document → DocumentVersion = **1 对多**；Drawing → DrawingVersion = **1 对多**。
- Meeting → MeetingMinutes = **1 对 1..N**（一次会议可有多版纪要）。
- 泛化关系：**任何来源载体（Email/EmailAttachment/Document/Drawing/Meeting/MeetingMinutes/Message）↔ 任何业务实体 均通过 SourceReference 多对多桥接**——这是追本溯源的统一通道。
- 其中 **一个文件/一张图纸可被多个项目事项（问题/任务/决策/计划活动/风险）同时引用**（关键多对多，见 B.4）。
- Evidence 可挂到任意实体（问题验证、风险佐证、决策依据），多对多。
- 邮件/会议/微信作为"外部进入渠道"，对应到 `IngestionJob`（见 A.6），保证可追溯与可重跑。

### A.4 问题/风险/任务闭环域

| 对象 | 一句话定义 |
|---|---|
| Issue（问题） | 一条问题（如设计冲突、现场偏离、接口争议），有状态机流转。 |
| Risk（风险） | 一条风险，有发生概率/影响等级/应对策略。 |
| Task（任务） | 一个分派到人的待办任务（可能来自问题/会议纪要/计划）。 |
| ActionMeasure（行动措施） | 为解决风险/问题而设的应对措施（risk 处置、issue 整改）。 |
| Decision（决策） | 一次决策记录（含决策人、结论、依据）。 |
| IssueStatusHistory 等（各 StatusHistory） | 各对象的状态流转历史。 |

**对象间业务关系（业务确认）**
- Issue → IssueStatusHistory = **1 对多**；Risk → RiskStatusHistory = **1 对多**；Task → TaskStatusHistory = **1 对多**。
- Issue ↔ PlanActivity = **多对多**（一个问题可挂多个计划活动，一个活动可带多个问题）。
- Issue ↔ Task = **1 对多**（一个问题可派生出多条整改任务）。
- Risk ↔ ActionMeasure = **1 对多**；Issue ↔ ActionMeasure = **1 对多**（可用同一 ActionMeasure 类型承载"整改措施"与"风险应对"）。
- Decison ↔ 任意被决策对象 = **多对多**（Decision 挂 Issue/方案/文件等依据）。
- 三者需各自记录**信息性质**(G5)：来源事实/已确认事实/AI 推断/预测/提案/决策。

### A.5 实体关系与知识域

| 对象 | 一句话定义 |
|---|---|
| Entity（实体） | 归一化后的"业务实体"（一艘船/一台设备/一个部位/一个厂商名…），等同于旧库"实体识别"概念的规范化。 |
| EntityRelationship（实体关系） | 实体之间的语义关系（同义/上下级/整机-部件/替换等）。 |
| EntityAlias（实体别名） | 同一实体的别名/简写/大小写变体/译名。 |
| EntityIdentifier（实体标识） | 实体在外部系统中的自然编号（设备编号、船号、图号等）。 |
| KnowledgeItem（知识条目） | 沉淀的业务知识结论。 |
| KnowledgeVersion（知识版本） | 知识条目的版本历史。 |

**对象间业务关系（业务确认）**
- Entity → EntityAlias = **1 对多**；Entity → EntityIdentifier = **1 对多**。
- Entity ↔ Entity = **多对多**（经 EntityRelationship）。
- Entity ↔ Document/Email/... = **多对多**（同一实体名出现在多个文件，经 SourceReference 桥接，并可被合并归并）。
- KnowledgeItem → KnowledgeVersion = **1 对多**；KnowledgeItem ↔ Entity = **多对多**（知识可关联多个被谈及的实体）。
- 别名合并需记录**关系来源与确认状态**（来源哪封邮件/哪份文件；已确认/待确认/拒绝）——见 B.5/B.6。

### A.6 AI 处理与系统治理域

| 对象 | 一句话定义 |
|---|---|
| IngestionJob（摄入作业） | 一次外部数据摄入（一封邮件/一个文件/一次会议）的运行实例。 |
| ExtractionResult（抽取结果） | 摄入后 AI/规则抽取出的候选实体、候选问题等（未审核）。 |
| ReviewQueue（人工审核队列） | 待人工确认的 AI 产出（抽取到的实体、识别到的问题、分类结果）。 |
| AiAnalysisRun（AI 分析运行） | 一次 AI 分析任务（摘要、归类、关系推断）的日志记录。 |
| AuditLog（审计日志） | 系统操作审计（谁在何时改了什么，含 AI 自动写入）。 |
| SystemConfig（系统配置） | 可配置项（不是硬编码的枚举由这里归口管理）。 |
| User（用户）/ Role（角色）/ Permission（权限） | 用户/角色/权限体系（Phase 后期启用，字段预留）。 |

**对象间业务关系（业务确认）**
- IngestionJob → ExtractionResult = **1 对多**；ExtractionResult → ReviewQueue = **1 对 N**。
- ReviewQueue → 目标实体（Issue/Entity/Knowledge 等）= **多对多**（一条审核项可生成多个实体；一个实体可由多条审核项支撑）。
- AiAnalysisRun 全局可挂在项目（或全局），与输入来源 SourceReference 多对多。
- User → Role = **多对多**；Role → Permission = **多对多**；各项操作写 AuditLog（**1 对多**）。
- 关键业务点：**AI 产出默认进入 ReviewQueue，人工确认后才能升级为 `CONFIRMED_FACT`；未经确认的只能保留 `AI_INFERENCE`/`SOURCE_FACT` 性质**。

## B. 关键业务规则确认（产品命令 → 须满足）

**B.1 项目 / 船舶 / 合同关系**
- **业务确认（确定）**：一个项目（Project）承载一艘主造对象（船/平台型），但为多合同驱动——船东/设计/船厂/分包/采购可由多份 **Organization×角色** 承载多合同，**不单独建合同表作为强制维度**，用 `Project↔Organization(角色)` + 关联文档来表达合同事实即可。若架构师需强合同实体，见 OQ-1。
- 一个项目只对应"一艘主造对象"为默认；若未来出现"多船一项目"（如船队），通过"项目×船舶实体"的多对多（Entity 域）扩展，**当前建模不封闭**。

**B.2 EPCS 阶段与专业/区域/系统的关系**
- **业务确认（确定）**：EPCS 是**时间维度纵轴**（阶段标签：Engineering/Procurement/Construction/Commissioning），专业/区域/系统是**横坐标维度**。二者正交，不互相嵌套。
- 一个业务对象（问题/文档/计划活动/风险/决策）除挂项 Project 外，**可同时打阶段 +（专业∪区域∪系统）多个标签**，用多对多标签关联承载，而非字段枚举。阶段允许出现"阶段不确定/跨阶段"并列情况，须可表达。
- **禁止**：把阶段做成 `status` 字段枚举而锁死跨阶段并列；应采用标签化/关联化表达。

**B.3 "问题→多个计划活动/邮件/会议/文件"的多对多**
- **业务确认（确定）**：Issue 与 PlanActivity、Email、Meeting/MeetingMinutes、Document、Drawing、Message、Evidence **全部多对多**，统一经 SourceReference/引用桥实现。这是"闭环可追踪"的核心，也是"一个问题可以被一张纸覆盖全貌"的产品能力（一页纸问题看板的数据前提）。
- 同一条 Evidence/证据可同时佐证多问题、多风险——多对多。

**B.4 "一个文件被多个项目事项引用"**
- **业务确认（确定）**：文件是"只读事实源"，可被多个（问题/任务/决策/计划活动/风险/知识）同时引用，多对多。文件端不可反向篡改（软删除/版本化，见 G4）。引用须带**上下文摘录/定位**（引用了哪一段/哪张图），便于回溯。

**B.5 如何避免同一问题在邮件/会议/任务中重复创建（全局实体标识）**
- **业务确认（确定）**：需要 **全局实体标识 + 别名/合并机制**：
  1. 摄入时 AI 抽取→进 ReviewQueue→人工确认（确认时人工可"合并到已有实体"或"新建"）。
  2. 系统在确认弹窗中**实时检索候选同名/近义实体**（靠 FTS5 trigram + EntityAlias）提示"此问题可能已存在"，人工选"合并"则并入已有实体并记录合并来源/确认状态（EntityRelationship 的 `synonym/merge` 关系）。
  3. 产品规则：**未确认的抽取结果绝不自动落地为正式 Issue**，杜绝重复污染。
- 这是"一处登记、全链路引用"的关键治理点，架构师在建模时要保证 ReviewQueue 与目标实体间有可回溯的合并链（OQ-2）。

**B.6 问题状态机确认**
- **业务确认（确定）** 状态机（主线 + 退回 + 重开）：
  `新发现(New) → 待确认(Triaging) → 已确认(Confirmed) → 已分派(Assigned) → 整改中(In_Progress) → 待验证(Pending_Verification) → 已关闭(Closed)`
  - **退回分支**：待确认→新发现（证据不足打回）；待验证→整改中（验证不通过退回重改）。
  - **重开**：已关闭(can be reopened)→已分派/整改中，需记录 reopen 原因与次数。
  - 每次流转写 IssueStatusHistory（含操作人、时间、信息性质、来源引用）。
  - 状态机本身产品已锁定，架构师建模时以"历史表 + 约束（合法转移）"落地；非法转移由应用层拒绝。

**B.7 计划基线不可被 AI 自动修改**
- **业务确认（确定）**：已批准基线(BaselineVersion)属**只读受保护**数据。AI/自动化**只可新增新的 PlanVersion/滚动预测版本，禁止改写已批准基线**；一切偏差以"实际进度(ProgressRecord) vs 基线"表达，而非改基线。基线变更仅允许人工权力操作（走 AuditLog + 变更授权）。
- 架构师须在建模上保证：基线一旦 `approved` 即只读；任何对基线字段的写操作在应用层被拦截并记审计（OQ-3）。

**B.8 信息性质分层（G5 落地规则）**
| 性质 | 可自动产生 | 是否可自动表为正式事实 |
|---|---|---|
| SOURCE_FACT 来源事实 | 是（解析原始内容原样落库） | 是（忠实原文） |
| CONFIRMED_FACT 已确认事实 | 否 | 仅人工确认后 |
| AI_INFERENCE AI 推断 | 是（AI 产出） | 否（进 ReviewQueue） |
| PREDICTION 预测 | 是（AI 滚动预测） | 否（计划预测类） |
| PROPOSAL 提案 | 是（AI 建议） | 否 |
| DECISION 决策 | 否（人工/仲裁） | 人工录入，可引 AI 依据 |

## C. 需架构师特别决策的开放问题（建模层，非产品已定）

| 编号 | 开放问题 | 产品倾向建议 |
|---|---|---|
| OQ-1 | 是否引入独立合同(Contract)强实体？ | 倾向"不强实体"，用 Project×Organization(角色)+关联文档承载；若建模允许动态扩展可加弱实体。 |
| OQ-2 | 全局实体标识的"合并链"如何落（实体↔源抽取项↔合并证据）如何保证不丢历史？ | 建议保留 ExtractionResult→ReviewQueue→Entity 的完整链，合并作为 EntityRelationship 关系并留证据指针。 |
| OQ-3 | "批准基线只读"在 SQLite 上如何强约束（触发器 vs 应用层）？ | 建议触发器主 + 应用层双保险，且写操作记 AuditLog。 |
| OQ-4 | 信息性质枚举应存"表枚举"还是"SystemConfig 可配置"？ | 建议 G5 枚举为产品固定枚举存表，但做成可扩展（未来可能新增性质），不硬编码为硬分隔。 |
| OQ-5 | 阶段(EPCS)+专业/区域/系统的"标签化"实现粒度：用单关联表统一还是分表？（影响查询性能与命中 FTS 的取舍） | 倾向统一"对象-维度-维度值"多值关联表 + 每值可检索，架构师权衡性能。 |
| OQ-6 | 版本化策略：文档/图纸/计划/知识统一版本机制 vs 各按需？（内容 hash、软删除、生效时间） | 倾向统一版本容器 + 软删除；具体 hash 粒度与快照策略由架构师定。 |
