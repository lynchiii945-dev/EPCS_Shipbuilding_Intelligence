## 1. 目标

在空库上建立可重复、可检验的迁移能力，并只落地域 1「项目与组织」的表结构，作为后续各域分批建表的基础。

本刀解决的问题：正式库还不能按设计建表，也没有幂等迁移和结构校验。

本刀不解决的问题：业务数据导入，邮件 / 文件摄入，计划 / 问题 / 知识 / AI 审核链，AVEVA 或图纸解析，完整权限平台，全量 24 张 FTS5 与 126 个触发器。

## 2. 范围

### 2.1 本刀要做的

1. 建立迁移框架
   - 新增 `01_Data/migrations/`
   - 幂等迁移运行器（建议 Python，与现有 `01_Data/scripts/init_db.py` 衔接）
   - 元信息表 `schema_version`，登记版本号和 `ddl_fingerprint`（对 `sqlite_master.sql` 排序拼接后计算 SHA256）
   - 结构一致性检查：用 `PRAGMA table_info` 逐列比对列名 / 类型 / notnull / 默认值，并比对索引、触发器、FTS 清单；与指纹不符则拒绝执行，不静默 `ALTER`
   - 单事务执行，失败整体回滚
   - 每个数据库连接都必须执行 `PRAGMA foreign_keys=ON`（连接工厂的强制职责，不能只写在迁移脚本首行）
   - `PRAGMA journal_mode=WAL`（库级，可持久化）
2. 仅创建域 1 的 17 张表（按真值源 §1 的 `CREATE TABLE` 清单）：
   - `schema_version`
   - `entity`（域 5 的实体主表在真值源中前置定义于域 1，本刀一并创建，因其 UUID CHECK 已覆盖）
   - `project`、`project_phase`
   - `organization`、`department`、`person`、`project_member`
   - `discipline`、`area`、`system`
   - `equipment_category`、`equipment`
   - `project_discipline`、`project_area`、`project_system`、`project_equipment`
3. 表结构、字段、约束以 R2 真值源为准，不改数据模型。
4. 可选且限于本域：按真值源 §7.7 的 B1 生成规则，仅为域 1 中有 FTS 映射的表生成虚表和同步触发器，用来验证生成器。禁止在本刀一次生成全部 24 张 FTS5 虚表和 126 个触发器。
5. 调整 `init_db.py`：取消「业务表数量应为 0」这一 Phase 1.1 断言，改为检查迁移后的域 1 对象，或把建表职责完全交给迁移运行器，由 `init_db.py` 只做环境与 FTS5 能力检查。
6. 自动化测试只使用 Python `:memory:` 或操作系统临时目录中的空库，不向 `01_Data/epcs_intelligence.db` 写入业务数据，不把 `.db` 提交进 Git。

## 4. 第一刀验收标准

1. 在空的临时库或内存库上，迁移可以一次成功完成。
2. 再跑一次：结构一致则跳过，不重复创建、不破坏已有结构。
3. 若有人改过表结构，再次迁移必须拒绝执行并报警，不得静默修改。
4. 新打开的连接上，`PRAGMA foreign_keys` 仍为 ON（由连接工厂保证）。
5. FTS5 trigram 中文检索自检仍然通过（沿用 Phase 1.1 的「集控台」类检查）。
6. 对象统计若已有域 1 表：使用 `PRAGMA table_list`，条件为 `type='table' AND name NOT LIKE 'sqlite_%'`，避免把系统目录算进去得到错误数量。
7. 自动化测试全部通过；测试不含业务数据；Git 提交不含 `.db`、日志、备份、原始资料、密钥或 `.env`。
8. 只通过云端拉取请求交付，不自动合并。拉取请求说明中写明实际创建的表、触发器、FTS 对象清单，以及未做事项。
9. 交付材料满足章程要求的可追溯性：分支、HEAD、差异范围、测试结果、已知问题和遗留事项。全表 UUID CHECK 目前仅覆盖 `project` / `entity` / `person`，本刀按真值源现状实施，并在交付报告中再次披露；是否在本刀扩大覆盖，听 GPT 在复审意见中的决定。
